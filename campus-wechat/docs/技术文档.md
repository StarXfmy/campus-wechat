## 1. 项目定位

同一个「校园木鱼」有两个入口：

| | 飞书端 | 微信端（本项目） |
|---|---|---|
| 载体 | 飞书自建应用机器人 | 微信个人号，跑在自己电脑上 |
| 大脑 | Python（22 个校园工具 + 三层分流） | **同一份 Python 大脑**，经本机 HTTP 调用 |
| 交互 | 交互卡片、按钮、分页 | 纯文本 |
| 在线 | 阿里云 24 小时 | 电脑开着才在 |
| 主动推送 | 早报、二课、自设提醒 | **无**（2026-11-16 起连自设提醒也不在微信端接） |

微信端不是飞书端的复制品，它解决的是另一个问题：**同学都在微信群里，不在飞书里**。要让木鱼真的被用起来，就得进微信。

而微信没有给个人号开放任何官方机器人接口。所以这个项目的主体工作，是在不改造微信客户端、不注入、不读内存的前提下，把「读消息 — 想一想 — 打字发回去」这条链路做稳，并且让它像一个正常人那样克制。

代码规模：微信桥接 `examples/wechatauto_bridge.py` 2092 行，是本项目的主体；聊天机器人骨架 `src/bot.js` 1716 行、`server.js` 1337 行来自上游，我在上面做了校园接入和行为改造。

## 2. 架构与数据流

### 2.1 四层链路

```
微信 PC 版（Weixin.exe，登录木鱼账号）
      │  ① 只读本地数据库收消息
      │  ② UIA 定位输入框打字发消息
      ▼
examples/wechatauto_bridge.py  ← 本项目主体（Python，含平台判定层 wx_behavior.py）
      │  POST http://127.0.0.1:8790/chat
      ▼
校园大脑（Python，与飞书同一份代码）
      ├─ handlers：规则路由 → 题库兜底 → Agent
      └─ 22 个工具 / 三层分流
```

三个进程，都要活着：微信、桥接、大脑。桥接和大脑之间走本机 HTTP，不出公网。
（2026-11-15 起中间层「鲸鲸娘」不再启动，保留它的目录只为需要时回退。）

### 2.2 单通道（2026-11-15 起）

> 早期设计有「大脑优先、失败退回本地模型」两条路。鲸鲸娘下线后本地模型一并停用：
> 大脑调不通就由桥接回一句「这个本鱼现在查不到，过会儿再问一次」，不再自己编答案。
> 下面保留最初的通道说明，供理解历史设计。

**通道一 · brain（现在唯一的路）**
`src/brain.js` 把消息 POST 给本机 8790 端口的 Python 大脑，请求体带 `platform: "wechat"`、`chatId`、`chatType`、`senderId`、`senderName`、`isMaster`。大脑那边知道这条来自微信、是不是主人发的，于是能正确套用「群里不答个人数据」「作业对主人直接写」这些规则。

超时 20 秒（`AbortController`），失败或返回空就 `return null`，调用方自动退回本地模型答。**大脑挂了，机器人还能聊天，只是查不到数据。**

**通道二 · campus（备路）**
`src/campus.js` 用 `execFile` 直接调 `hduhelp-cli`，不经 Python。它只认空教室类问题：

```js
const QUERY_RE = /(空教室|空课室|空的教室|有(没有)?空(教室|位|房)|哪里(能|可以)?自习|去哪(儿)?自习|哪个教室(空|没人|有位置)|自习室)/;
```

十种问法都覆盖到，并且能把「正心」「创智」「青越」「芯越」「精诚」「博约」「礼贤」「子衿」「6 教南」「D 楼」「第 6 教研楼」这些学生嘴里的叫法，映射成接口要的楼栋代码。绍兴校区的五栋（ZX/CZ/QY/XY/JC）单独标出，问「绍兴哪里自习」不会返回下沙的教室。

这里有两个坑值得记：
- 接口返回的 JSON 尾巴上会跟着「有版本更新」提示，直接 `JSON.parse` 必炸。所以写了 `parseFirstJson()`，从最后一个 `}` 往前逐个试，直到能解析为止。
- 楼栋代码 `9999`（待定/校际选修）和 `ts`（上课通知）不是真实教室，混在结果里会说出「去 9999 自习」这种话，所以直接进 `SKIP` 集合过滤掉。

### 2.3 身份认证只有一份

`src/master.js` 是全项目唯一判断「这条消息是不是主人发的」的地方，判定顺序写死在文件头注释里：

1. `senderId` 命中 `master.wxids` → 是主人。这是微信内部 id，改昵称冒充不了。
2. 非微信渠道（网页、抖音）没有稳定 id，昵称对上就算。
3. **微信里，只有当 `master.wxids` 里一个「像 wxid 的值」都没有时，才退回用昵称认。**

第 3 条是安全设计：微信里谁都能改昵称，配了真 wxid 还认昵称，等于给所有人开后门。旧版就是因为这条没做，出现「调试台说认你是主人、微信里却当陌生人」——跑消息的 `bot.js` 和出预览的 `server.js` 各写了一套规则。现在两边都调 `matchMaster()`，返回结果里带 `reason`（`wxid` / `nickname` / `name_blocked`），`name_blocked` 就是「昵称对上了但被规则 3 挡住」，排查时一眼能看出为什么没认。

## 4. 防封号与群聊行为设计

微信对自动化行为是封号的，规则不透明。所以这个项目里最花心思的不是「怎么让她能答」，而是**怎么让她少说话**。八条机制，全部有代码依据：

| 机制 | 参数 | 代码位置 | 为什么 |
|---|---|---|---|
| 必须 @ 才回 | `group.requireAt: true` | `config.json` | 群里主动插话是最容易被举报的行为 |
| 不主动接话 | `freeChat: false` | 同上 | 关掉「偶尔接一句」，宁可显得迟钝 |
| 回复冷却 | `cooldownSec: 30` | 同上 | 非主人两次回复最少隔 30 秒；冷却期内的提问**排队补答**，不丢 |
| 随机延迟 | `replyDelayMin/Max: 3–8` + `minTotalMs: 6000` | 同上 | 每次回复前随机等，且总耗时不低于 6 秒——秒回是机器的特征 |
| 每小时上限 | `maxRepliesPerHour: 20` | 同上 | 量级压在正常人范围内 |
| 主人也不例外 | `masterAlwaysReply: false` | 同上 | 群里主人不 @ 同样不回，避免「主人在时她特别活跃」这种模式 |
| 深夜沉默 | 群聊 22:00–08:00 只回主人 | 人设 + 运行时 | 半夜在 1000 人群里说话最扎眼 |
| 失败即拉黑会话 | `fail_streak >= 2` → `dead_chats` | `wechatauto_bridge.py:1009` | 发不出去就停，绝不重试刷屏 |

另外三条是「像人」的细节：

- **游戏避让**：`gameWhitelist` 里的程序（如 valorant）在跑时，完全不碰微信窗口，回复进 `pending_replies` 排队，等你退出再发；排队消息 5 分钟过期（`queuedMaxAgeSec`），过期就不发了——不会打完游戏突然收到三分钟前该说的话。
- **低电量收尾**：笔记本电量低于 5% 时主动说一句「晚安，电量快没了，我先睡啦」，而不是突然失联。
- **被移出群就永久跳过**：`group_is_alive()` 检查群里还有没有她，被踢了不再尝试发送。

### 红包提醒的边界

群里来红包时，她只在群里喊一嗓子（「红包来了，本鱼喊一声」这类随机文案），**不点、不领、不进大脑分析**。深夜有红包也不喊。

这条边界很重要：自动领红包是明确的违规操作，只做「通知人类」这一件事。

## 5. 四个真实 bug 的排查过程

这部分是我最想写的——三个 bug 都不是「功能没做」，而是「看起来能用，实际坏了」，排查方式完全不同。

### 5.1 作用域错误：整条回复链路停摆 15 天

**现象**：机器人算出了答案，日志里也有完整回复文本，但微信里就是收不到。日志只显示：

```
UIA 发送异常（第 1 次，0.0s）：NameError(name 'chat_display_name' is not defined)
UIA 发送异常（第 2 次，0.0s）：NameError(name 'chat_display_name' is not defined)
UIA 发不出去，跳过 OCR 兜底： <某个群名>
发送最终失败，请把微信窗口保持在桌面、别最小化
```

**排查**：`0.0s` 就抛异常，说明根本没走到发送，炸在发送前的准备阶段。定位到 `with_window_on_top(fn)`：

```python
def with_window_on_top(fn):
    ...
    SEND_STATE["who"] = chat_display_name   # ← 这是调用方 send_text() 的参数
    SEND_STATE["text"] = (text or "")[:40]  # ← 同样拿不到
```

`with_window_on_top` 和 `send_text` 是**兄弟函数**（都定义在 `main()` 里），前者拿不到后者的参数。这段是后来加调试信息时写错的。

**为什么难发现**：异常被上层 `except` 吞掉，只留下一句「UIA 发不出去」，看起来像微信窗口的问题（所以还提示"别最小化"），把排查方向带偏。

**修法**：给 `with_window_on_top` 加两个可选参数 `who`、`text`，6 处调用把会话名和内容传进去。诊断信息保留，作用域问题解决。

**教训**：Python 里引用不属于当前作用域的变量，写的时候不会报错，运行时才炸，而且炸点可能离病灶很远——因为中间有 try/except 把信息吃了。

### 5.2 wxgf 容器：「有时能认、有时不能」

**现象**：发图片问「这是什么」，有时候能正确描述，有时候回「图片输入格式/解析错误」。

**根因**：微信 PC 版存图片用的是 **wxgf 容器（内含 HEVC 编码）**，不是标准 JPEG/PNG。旧代码按文件扩展名判断格式，把 wxgf 当 JPEG 发给视觉接口——接口能不能吃下这个文件，取决于那张图恰好是什么编码，所以表现为「有时行有时不行」。

**修法**：按**文件头**判格式，识别出 wxgf 就先转成 JPEG 再发。

这条修完，看图功能从「碰运气」变成稳定可用。

### 5.3 身份争执被喂回模型：认了主人还是不认

**现象**：调试台改了主人名单，微信里她仍然说「你不是我主人」。

**两层原因**：
1. `bot.js`（跑消息）和 `server.js`（调试台预览）各写一套识别规则，两边结论不一致 → 统一成 `matchMaster()`。
2. 更隐蔽的一层：识别修好之后**还是不行**。因为那个会话的历史里已经存了几十条「你不是主人」，模型顺着自己的历史继续否认。实测 51 轮历史里连问两遍，两遍都答「不是」。

**修法**：三管齐下——提示词里加【身份纠错】规则；喂给模型的历史**剔除身份争执那几条**（记忆文件本身不动，保留原始记录）；万一回复仍然否认，`finalize()` 兜底改成认下来。

**这条最有价值的地方**：它说明模型的行为不只由当前配置决定，还由你喂给它的上下文决定。改配置不管用时，要看上下文里有什么。

### 5.4 群里 @ 完再发表情包，它当没被叫到

**现象**：11-16 录演示，先打「@木鱼」发出去，紧跟着发一张表情包。日志里图片识别**成功**了，回复却没有——原因是同一条判断链上打了一句 `not_addressed`，直接丢弃。

**为什么**：桥接层判断「这条有没有在叫我」只看**当前这条消息**的正文。表情包的消息体里没有文字，只有一个图片载荷，所以「@木鱼 → 发表情」这个顺序里，第二条永远被判成「没叫我」。反过来先发表情再 @，第一条照样丢。

**修法**：识别图片消息时，把「上一条是不是在叫它」这个信息带进来。

```python
_is_follow_at = False           # 每条消息单独算，不跨条保留
...
if 命中 _next_media:            # 这条是刚识别出来的媒体消息
    _is_follow_at = True
addressed = _is_follow_at or any(k in text for k in 叫法)
```

关键在**它是每条消息的局部变量，不是一个跨消息的状态位**。识别失败的分支里有好几条 `return`，如果用全局标记，一次识别失败会把标记留在身上，下一条普通文字消息就被误判成「在叫它」——那是把一个 bug 换成另一个更难的 bug。

**这条最有价值的地方**：「@ 之后再补一条」是人类在群聊里最自然的说法，但代码里的「一条」是原子单位。凡是按条判断的地方，都要问一遍「用户会不会把它拆成两条发」。

### 6.3 这一轮（2026-11-16 凌晨）改了什么

录完演示逐条复盘，暴露出五个问题，三个是真 bug、两个是「按设计但设计不对」。文件行号是当前仓库的真实位置，`app/…` 在**大脑仓库**，`examples/…` 在本仓库。

| 现象 | 根因 | 改动 |
|---|---|---|
| 问「我这周校园卡开销如何」答成余额 | 「校园卡 / 饭卡」是裸名词，谁先抢到谁答，余额规则排在消费前面 | `router.py` 把裸名词从余额关键词里摘掉，只留「余额 / 还剩 / 卡里还有」这类带方向的词 |
| 「上周校园卡开销如何」跑去答校园卡使用说明 | 「如何 / 怎么 / 在哪」这类疑问词被无条件当成操作类问题去查题库 | `handlers.py:_faq_worthy` 收窄成「只在意图不明时」才按疑问词查题库；补办挂失类改成按文本判，不再依赖意图名 |
| 同一张卡，微信查 9 笔、飞书查 5 笔 | `expense_log` 按 `chat_id` 分仓，两个入口各存一份 | `records.py:35` 唯一键改成 `UNIQUE(happened_at, amount)`，汇总查询不再带 `chat_id` 过滤；`sync_bitable.py:113` 流水改成行级合并（`day + 金额 + 店名` 判重），覆盖式同步会把对端刚记的那笔冲掉 |
| 「30 秒后提醒我」时灵时不灵 | 模型抽时间只到分钟，同一句话有时算出过去的时间就判过期；事项为空时整条中止 | `memory.py:78` 新增相对时间解析（秒 / 分钟 / 小时 + 中文数字，算不出未来就 +1 分钟）；`handlers.py` 事项抽取失败时用代码兜底：剥掉时间短语和「提醒我」，剩下的就是要做的事 |
| 群里一句话回两百字 | 群聊没有字数上限 | `http_bridge.py:214` 单段回复压到 70 字，截在句末标点；带换行的清单、课表豁免 |
| 天气「又查不到」 | 这台机器到 open-meteo 正常 2.8 秒，但实测出现过整段不通（>20 秒）；失败后冷却 60 秒，下一个话题也拿不到预报 | `weather.py:242` 冷却 60 → 15 秒，拉取失败立刻原地重试一次 |
| @ 完再发表情包，它当没被叫到 | 「有没有叫我」只看当前这条的正文，图片没有正文 | 见 5.4，`wechatauto_bridge.py:1660` |
| 历史越积越长，接话接四小时前的话题 | `conversations` 只按条数滚动，不看时间 | 主人指令「清空上下文」：`handlers.py:1376` 只认短句（「清空购物车」不算），`handlers.py:1384` 报删了几条，并说明长期记忆和课表没动；微信端只认主人 |
| 答应了提醒却永远不推 | `reminders` 到点没有任何链路写进 `wx_outbox` | `http_bridge.py:187` 微信入口拦下提醒类意图；`http_bridge.py:199` 连追问里的「设个提醒」一起过滤 |

回归测试在 `tests/test_fixes_1116.py`，12 组 77 条断言，自测数据写在 `__selftest_1116__` 这个会话名下、跑完按这个 key 删干净。

## 7. 设计取舍

这一章写的不是「做了什么」，而是「为什么这么做、放弃了什么、代价是什么」。每一条都是当时真的权衡过两三个方案。

### 7.1 接入方式：UI 自动化，而不是 hook 或协议

| | 说明 |
|---|---|
| **选择** | 只读本地数据库收消息 + UIA 模拟打字发送 |
| **放弃** | hook 注入、协议号、wechaty、企业微信 |
| **为什么** | hook 要往微信进程注入 DLL，社区经验里这是封号最快最稳的一种方式，而且改了客户端行为，出了问题无法归因。wechaty 的网页协议早就失效，个人号协议同样是高危。企业微信只能在自己组织的群里跑，进不了同学的微信群。UI 自动化不注入、不改客户端、不写内存，行为上最接近「一个人坐在那里打字」。 |
| **代价** | 慢——一条回复 6–15 秒，发一张图 23–39 秒；电脑必须开着、窗口不能被挡；OCR 兜底这条路在这台机器上会卡在截屏里，所以上了 25 秒超时直接放弃这条消息，而不是硬等。 |

### 7.2 数据库：只读，不写

桥接连微信数据库时明确只读（日志里那句「连接微信 4.x 数据库（只读）」）。收消息靠读，发消息靠打字。

**为什么不直接往数据库写一条**：那样能秒发、能伪造任何发送者，技术上确实省事。但写别人的数据库是明确的越界行为，而且微信版本一升级、库结构一变，写坏就是丢聊天记录。省下的那十几秒不值得。

### 7.3 红包：只提醒，不代领

```python
def announce_red_packet(username):
    """群里来了红包，喊一句。只提醒，不点、不领。"""
```

**选择**：识别到红包消息，在群里发一句「红包来了，本鱼喊一声」，然后不动。深夜（22:00–08:00）连喊都不喊。
**放弃**：自动点开、自动领取。
**为什么**：领红包是资金操作。自动领别人的红包，性质上已经不是「助手」而是「脚本抢钱」，一旦出问题没有任何可辩解的余地。提醒只是信息传递——她看到了，告诉人，人自己去点。
**代价**：她「不能帮忙干活」，演示时这条看起来不够炫。但这条线划在哪儿，决定了这个项目能不能公开拿出来讲。

### 7.4 主动推送：全部放回飞书端

微信端现在**一类主动消息都不留**。早报、二课新活动、记忆到点提醒在 11-15 就关了；11-16 连「用户自己设的提醒」也从微信入口摘掉。

```python
WECHAT_PUSH_ENABLED = False   # 微信端主动推送总开关
ACTIVITY_ENABLED = False      # 二课新活动改到飞书推
_REMIND_INTENTS = frozenset({"remind", "edit_remind", "cancel_remind", "my_reminders"})
```

摘提醒这条不是「嫌麻烦」。查了一遍发送链路：`push_scheduler.pending()` 只读 `wx_outbox`，而只有早报和二课会往 `wx_outbox` 写——`reminders` 表里到点的记录，微信端**没有任何一条路径会把它发出去**。也就是说用户设完会得到一句「好的，两点十分提醒你」，然后永远等不到。这种空头支票比不做更糟。

所以微信入口现在遇到提醒类说法会直接讲清楚：记了也发不出来，请去飞书那边设。同时把回复末尾「你可能还想问」里的「设个提醒 / 我的提醒有哪些」也过滤掉——推荐一个点不动的选项，等于第二次承诺。

**为什么**：主动发消息是封号权重最高的行为——不是「回复得快」，而是「没人叫你你自己出来说话」。而且微信端要电脑开着才在线，凌晨两点机器开着、群里安静，它突然冒一句「今天的课表…」，这个画面本身就足够可疑。飞书端跑在阿里云上，24 小时在线、有官方接口、平台本来就允许机器人主动发消息，可靠性差一个量级。
**代价**：同一个助手在两个入口的行为不一致，得在文档里解释清楚为什么；而且飞书那边能设提醒、微信这边不能，用户会问「为什么这里不行」。

### 7.5 白名单：宁可「不响应」，也不「全响应」

群白名单是硬编码的一份列表。测试群一开始不在里面，@ 她没反应。

**为什么不图省事把列表清空**（空列表等于所有群都响应）：那样调试确实快，但一旦带着空列表跑起来，1005 人的真实群也会跟着响应。在几百人的群里说错一句话，代价不是「丢人」两个字能盖过去的。
**改法**：保留默认拒绝，但把「静默拒绝」改成可诊断——未命中时打一行日志，把系统实际认出来的群名和群 ID 写出来。

```python
log("白名单未命中，已忽略：群名=「%s」 ID=%s" % (shown, username))
```

**为什么这条值得单写**：默认拒绝是对的，但**静默的**默认拒绝是个坏设计——用户遇到「她不回话」时完全没有线索，只能瞎猜是网络、是窗口、还是模型的问题。安全性保留，可观测性补上，两头都要。

### 7.6 人设里禁止说「工具」「接口」「数据源」

人设有一条硬规则：不许说「这个工具没返回」「系统里没这块数据」，查不到就说「这个本鱼不知道」。

**为什么**：微信群里坐着一群不懂技术的人，「我调用的接口 500 了」这句话除了暴露这是个机器人之外没有任何信息量。而且一旦她开始解释技术细节，群友就会开始试探边界——「那你帮我发个消息给某某」。
**代价**：出问题时她自己也说不清为什么，排查只能靠日志。这是有意的取舍：**对用户隐瞒实现，对自己保留全部日志**。

### 7.7 大脑与接入层分成两个仓库

校园查询能力在 `campus-muyu`（Python），微信接入在这个仓库。

**为什么不合成一个**：

| 理由 | 说明 |
|---|---|
| 许可证边界 | 这个仓库基于 MIT 上游改造，要保留上游版权声明；`campus-muyu` 全部自己写的。混在一起，整个仓库的授权性质就说不清了 |
| 运行环境不同 | 大脑跑在阿里云 Linux，接入层只能跑在 Windows（微信 PC 版没有 Linux 客户端） |
| 故障隔离 | 微信端挂了不影响飞书端；大脑升级不用重测微信接入 |
| 复用 | 以后接抖音、接网页，都是再接一个壳，大脑不动 |

**代价**：两端要同步。做法是每次改完大脑就从本机推一份上云，靠多维表格双向同步数据（记忆、课表、消费），15 秒一轮。



## 8. 局限与未做

| 局限 | 原因 | 影响 |
|---|---|---|
| 电脑必须开着、微信窗口不能被挡 | UI 自动化的固有限制 | 人不在电脑前时她不上线 |
| 有封号风险 | 微信不开放个人号机器人接口 | 已用第 4 章八条机制压行为，但风险不为零，账号是专用小号 |
| 发消息慢 | UIA 打字 + 随机延迟 + 冷却 | 一条回复 6–15 秒，比 API 慢一个量级 |
| 发图片慢 | 粘贴 + 定位，实测一张 23–39 秒 | 演示时不用发图 |
| OCR 兜底会卡死 | `PIL.ImageGrab.grab` 在这台机器上会挂住 | 已改成 UIA 可用时不走 OCR，且给 25 秒超时直接放弃 |
| 群成员隐私 | 群里消息会进模型上下文 | 人设里明确禁止外泄个人数据，群里不答余额/成绩/课表 |
| 没有卡片 | 微信纯文本 | 清单整条发出；超过 1200 字按空行自动分段 |

**明确不做的**：自动领红包、自动加好友、自动进群、代发消息给指定人、读取好友列表。这些要么明确违规，要么越界。

## 9. 部署与运行

### 9.1 三个进程

| 进程 | 启动方式 | 端口 |
|---|---|---|
| 微信 PC 版 | 手动登录（用专用账号） | — |
| 校园大脑 | `campus-feishu-agent` 的 `启动微信大脑.bat` | 127.0.0.1:8790 |
| 微信桥接 | `campus-feishu-agent` 的 `启动微信桥接.bat`（先起大脑再起它） | — |

### 9.2 首次配置

1. 复制 `config.example.json` 为 `config.json`
2. 填模型服务商的 `apiKey`
3. 填 `persona.master.wxids`（你自己的微信内部 id，调试台里有「最近说过话的人」可以照着抄）
4. 填 `examples/wechatauto_bridge.py` 第 47 行的 `ONLY_CHATS`（要响应的群名）
5. 填 `brain.baseUrl`（本机就是 `http://127.0.0.1:8790`）
6. 双击 `1-诊断环境.bat`，再双击 `一键修复并自检.bat`——自检会真的发一条消息并用数据库证实

### 9.3 排障顺序

遇到「她不回话」，按这个顺序查，不要凭感觉：

1. `data/wechat-bridge-4x.log` 最后几行——有没有「收到」？没有就是数据库连接或白名单问题
2. 有「收到」但出现「白名单未命中，已忽略：群名=「XXX」」——照抄 XXX 补进 `ONLY_CHATS`（这是新加的诊断，以前这里静默无日志）
3. 有「收到」也有回复文本，但没有「发送成功」——看异常类型：`NameError` 是代码问题，`找不到主窗` 是微信缩到托盘了
4. 「UIA 不可用」——跑 `一键修复并自检.bat`，看是不是微信版本更新导致 RVA 变了

## 附：与飞书端的关系

两个仓库、一份大脑。校园查询能力全部在 `campus-feishu-agent` 的 Python 侧，微信端通过 `brain.js` 调它，所以：

- 飞书端加了新工具，微信端**自动能用**（同一份代码）
- 微信端只负责「怎么进微信、怎么不发疯」
- 数据（记忆、课表、消费）两端共享，靠多维表格双向同步

这也是这个项目最值得说的设计：**接入层和大脑彻底分开**。换掉微信这套，大脑不用动；反过来也一样。
